# 宿主集成说明（给客户端/宿主方）

本技能是**本地、离线**的经验档案工具：一切读写都在用户本机的私人目录里完成，不联网、不上传。
它对宿主只有四项诉求——宿主不做也不会坏，但做了效果明显更好；末尾列出宿主**不应做**的事。

## 1. 把技能放在独占目录

少数宿主在「上传/添加技能」时会往技能根目录写入自己的簿记文件（例如 `_user_meta.json`）。
这类文件不是核心内容，但会让核心校验默认判定"多出文件"：`doctor` / `intro` / 升级 / 备份的
核心校验失败（日常 status/recall/query/add 不受影响）。能指定安装目录时请让它独立；确实无法
避免时，用户可显式放行：`python -B scripts/core_package.py verify --allow-host-files`。

## 2. 成对注入账号作用域（可选，用于同机多用户隔离）

- 同时提供 `REVIEW_EVOLUTION_CLIENT` 与 `REVIEW_EVOLUTION_ACCOUNT`：技能按 **(客户端, 账号)**
  解析档案——同一用户的多个客户端可绑到同一主档案（经验共享），不同用户绑到各自档案（互相不可见）。
- **两个都不提供**：退回单默认绑定模式（整台机器共用一份档案），适合单人机器。
- **只提供一个**：命令会明确报错，请成对注入。
- 新作用域首次出现时技能会提示"未绑定"，由用户人工 `bind` 选择档案。**宿主不要替用户猜账号归属**，
  也不要自动新建空档案——绑到空档案会读不到旧经验（技能会给出提醒）。

## 3. 会话启动提示（建议，一句即可）

在会话开始时注入一行上下文，例如：

> 本机有本地经验档案（profile_id 前 8 位 <xxxx>，共 N 条）。相关任务开工前建议先查一次经验。

取不到条数时，只提示"本机有本地经验档案"也有价值。**不要注入档案正文**，也不要把私人目录内容
放进系统提示或项目上下文。

## 4. 技能加载触发词（建议在宿主的技能索引里登记）

中文：经验复盘、收尾复盘、自我迭代、技能进化、理解用户习惯、个性化、长期记忆、习惯校准、
减少重复追问、跨设备经验整合。
English: retrospective, reflection, lessons learned, self-iteration, understand user habits,
personalization, long-term memory, habit calibration, cross-device merge.

## 宿主不应做的事

- 不要把私人数据目录（用户数据目录下的 `review-evolution`）加为"工作区/源目录"：那会让明文
  JSON 进入项目级搜索与分享范围。允许写入但不进入项目视野，才是正确的授权方式。
- 不要在技能目录里写运行产物（计划文件、日志、导出包）；也不要让 `--profile` 指向技能目录。
- 不要替用户执行写入、导入、导出或发布——这些按技能规则需要用户逐次确认。
- 宿主自身提供"记忆/账号档案"能力时，本技能不与之竞争：把本技能当作可核验的本地档案层即可。
  **但要给用户两条路**（2026-09-12 实测教训）：宿主自带记忆时，用户说"记住…"往往被宿主记忆接走、
  技能侧根本没被调用。请在界面上允许/提示"也写入技能档案"，至少**不要阻止**技能侧的写入；
  技能侧规则是**默认双写**，只有用户明确说"只让宿主记"才跳过。

## 集成自检（4 步）

1. 技能目录除清单文件外没有别的文件：`python -B scripts/core_package.py verify` 输出正常；
2. 注入账号变量后 `python -B scripts/experience.py contexts` 能显示当前作用域与绑定；
3. 新会话里问"这个技能怎么用"，能拿到首次介绍；
4. 相关任务开工前能看到一次经验查询动作（可由宿主日志核对）。

## 5. 上传/注册路径不要改写已装文件（2026-09-12 真机实测）

实测：某客户端在「上传/添加技能」路径会**改写已装 `SKILL.md`**——把 frontmatter 的
`description: >` 改成 `description: |`（折叠换行压平），并注入 `install_method: upload` 之类的字段。
后果不是"少了个功能"，而是**升级第一步就被拒**：文件字节变了、清单摘要还是发布原值，
核心完整性校验直接失败（本技能不会为它自动放行）。

**给宿主的建议**：注册环节**只读**技能目录，不要把规范化后的文本回写磁盘；若确实必须回写，
请回写后**同时更新清单摘要**（即等价于对技能做了一次修改），并在注册表里保留原始摘要以便区分。
**给用户的处置**：见 [安装与迁移](install.md) 的 U1 小节（备份 → 用同版本原包复原 → 重新 verify；
用 `core_package.py diff --root … --reference …` 只读判断"是否只是表示法差异"）。

## 6. 同一台机器可能有多份安装（2026-09-12）

用户可能在 Codex、钉钉千问、其它客户端里**各装一份**，甚至**版本不同**（实测：
`.codex\skills\wb-review-evolution` 0.21.5 与 `.qwenworkcn\skills\review-evolution` 0.22.6
共用同一个默认档案）。这是预期行为，不是缺陷——但会造成两类误会：

1. "A 客户端怎么看不到 B 客户端装的那份？"——各自独立目录，本来就不会互相发现；
2. 检查/验收/自检**测错了对象**：`doctor` 现在会列出本机发现的所有安装与版本（`installations`），
   版本不一致时给出提示。**任何验收都要先确认"测的是哪一份"**，不要默认只有一个安装。
