# 兼容与降级边界矩阵

核对日期：2026-09-12；当前 **v1.0.0（受限范围正式版）**。本版相对 `v0.22.10-beta.1` **无业务逻辑改动**，变更集中在正式发布所必需的一致性：版本升 `1.0.0` 且 `release_ready=true`（stable 通道要求）；**支持范围口径修正为"一个 OS 账户（由同一个人使用）+ 该账户下已实测的一个或多个客户端"**——隔离单位是 OS 账户，不是使用者人数或客户端个数，且**不承诺同一账户下多使用者之间的经验隔离**；新增 `SECURITY.md` 与 `.github/ISSUE_TEMPLATE/` 并纳入核心清单与发布门禁白名单，使"仓库内容 = 公开候选 = 安装包"三者一致。此前同日变更：手机端口径、与宿主原生记忆的关系、`diff` 键名解析补全、技能描述校准与多语言硬要求。

## 支持范围与证据层级（2026-09-10）

状态分三层，避免把“能运行”写成“完整验收通过”：

1. **完整验收通过**：明确版本组合完成入口、安装、绑定、读写、召回、新会话写入、恢复，
   并有 A/B/C 证据。**Windows + 钉钉千问办公客户端已于 2026-09-12 取得 A/B/C 三会话旅程证据**
   （v0.22.8-beta.1：A 有介绍且主动说明"默认双写"规则、B 写入 1 条、C 按 record id 检索回该条）；
   但该组合的**恢复**仍只有"候选副本 + 合成档案"证据，故仍未满足第 1 层全部条件。
   其余情况：Windows + Codex 具备本机完整验收与
   **真实第二环境的升级/失败恢复自动验收（6/6 PASS，桌面双击与宿主客户端两条路径）**，
   但自然语言三会话旅程（A 安装 / B 请求加载并写入 / C 读回新增）仍只有部分证据。
2. **真实环境已观察可用（初步验收）**：Windows + Codex、Windows + 钉钉千问办公客户端
   （≥5 台安装成功、初步升级验收通过）、钉钉内嵌千问（用户实际安装/使用反馈显示可运行）。
   该层表示有真实安装/使用或初步验收证据，**不等于**完整 A/B/C 验收通过；
   版本、入口与绑定持久性仍需逐组合登记。
   其中 Windows + 钉钉千问办公客户端已有真实第二环境的升级/失败恢复验收证据（见下表）。
3. **小范围验证成功，但不保证完整支持所有移动端（2026-09-12 定）**：**手机端**（华为 Mate 80 +
   鸿蒙 7.0 钉钉内嵌千问 / WorkBuddy 客户端）**在单对话内安装与使用已小范围验证成功**（真实用户
   实测），但实测表现为**对话级独立沙箱**：技能安装在某一对话的沙箱内，其它对话看不到、调不到
   该技能，也读不到同一份经验档案；技能可见性另有一层"会话启动时定稿的能力清单"，运行期不刷新。
   因此手机端**只按"小范围可用"表述，不保证完整支持所有移动端**：跨对话调用与经验累积尚未打通，
   暂停深度验证；待宿主提供应用级共享技能目录与账户级经验存储后再评估。
4. **未验证**：Android 钉钉、iOS、其他 App 级宿主、同机不同用户的 OS 权限级隔离等；
   未实测不得写“支持”。移动端组合登记详见 HM-00。

**平台口径拆分（2026-09-11 明确，避免把一件事说成两件）**：

- **备份 / 恢复（目录发布）**：`profile_backup.publish_directory()` 在非 Windows **明确拒绝**
  （`Directory publication currently validated on Windows only`）。所以这一功能**仅 Windows 可用**，
  是**设计上的限制**、不是缺陷；用户当前也无非 Windows 实测条件，故保持限制并在文档声明。
- **普通记录 / 查询 / 召回 / 导出**：代码按跨平台写（写锁有 `msvcrt`/`fcntl` 双分支，数据目录有
  Windows / macOS / Linux(`XDG_DATA_HOME`) 三分支），但**从未在非 Windows 真机跑过** →
  属"未验证"，不宣称支持。
- **其它宿主客户端（Claude Code 等）**：技能目录与加载机制随客户端而异，**必须按各自官方文档
  核验**，不得沿用钉钉/千问的路径假设；未实测不得写"支持"。
- **手机端（对话级沙箱）**：手机客户端的技能与经验按对话隔离——装在哪个对话就只在那个对话可用，
  换个对话既读不到技能也读不到经验。这是宿主架构限制，不是本技能可自行绕过的配置问题；
  因此手机端口径定为"**小范围验证成功，但不保证完整支持所有移动端**"，不写"已支持移动端"，
  也不以单次安装成功推断跨对话可用或"完整支持移动端"。
- **模拟环境的边界**：用三平台 CI 可以验证**代码层**是否跨平台（含锁、路径解析、编码），
  但**验证不了**宿主客户端的加载与触发、授权弹窗、真实对话中的召回/写入效果与跨端整合旅程——
  这些必须真机。CI 结果不得用于对外宣称"支持 macOS/Linux/某客户端"。

## CLI 参数变更记录（破坏性变更，U6；2026-09-12 起维护）

历史作业脚本会**静默失效**，因为 argparse 只在运行时才知道参数形态变了。出现新变更时在此追加一行。

| 版本 | 命令 | 变更 | 旧写法 | 新写法 |
|---|---|---|---|---|
| v0.21.x | `release_update.py plan-install/install` | `--candidate` 不是选项 | `--candidate <目录>` | **位置参数** `<candidate>`（v0.22.6 起 `--candidate <目录>` 也接受，作为兼容别名） |
| v0.22.x | `experience.py plan-export/export` | `--components` 变为**必填** | 省略 `--components` | 显式 `--components s1 s2` |
| v0.22.7 | `core_package.py` | 新增只读诊断子命令 | — | `diff --root <目录> [--reference <原包目录>]` |
| v0.22.7 | `release_update.py` | 新增收据模板子命令 | 手工编写 `component-review` 收据 | `emit-receipt-template --candidate <目录> --target <技能目录> --out <新文件>` |

`release_update.py` 的 argparse 报错已追加一行指向本节；`check` 也不再把手写脚本引到
`VALIDATION_ERROR` 这个混合状态上——**本机核心自身失效**现在返回 `LOCAL_CORE_INVALID`（U7）。

## 维护基线

最低起点 v0.21.5-beta.1（用户于2026-09-09变更要求）。未来版本需保留从该基线升级的可行路径；重大性能或能力变化导致无法兼顾时必须说明理由与经验保留办法。更早版本不再作为发布验收前置；这不是删除历史经验或主动拒绝可读旧数据的授权。

核心 modular-1、core_api=1、data_schema=1 不变；profile、installation、pack 格式1不变。S1政策 plan-a-v1，只有S1计分。
API1与分类 core_api=2 的API2经验包继续支持；最低安装版本与数据交换格式不是同一概念，不能因调整升级基线删除跨客户端协议或身份审查。

**导出端与内容格式必须一致（D8）**：包里只要有分类字段（`s2_type`），清单就必须声明 `core_api=2`。
当前版本按内容自动判定（有分类即 2），但**用更旧的核心导出时不会**——那一侧的包会声明
`core_api=1` 却在正文里写分类字段，结果是"导出端成功、导入端才被拒绝"。遇到这种滞后失败，
处理办法是用与内容匹配的核心重新导出，不要通过改包内清单绕过（清单哈希与 `pack_id` 会一起失配）。

## 升级与恢复

1. 使用v0.21.5自带可信更新器 plan-install/install，明确实际目标和候选版本；新增组件仍须reviewed-manifest，计划绑定实际字节。无需早期版本候选更新器bootstrap例外。
2. 保存完整旧核心和档案备份及revision/记录/有效偏好基线；升级后核验档案不变，再做续写读回。不得重建空档案、变更profile_id或混入其他用户数据。
3. 同代身份变更门禁、schema/API变化停止、事务及失败回滚保护保留；不把取消旧版维护当作放宽安装安全检查。
4. backup/restore仍要求reader_core的完整核心摘要匹配；需保留对应核心。跨版本恢复不能仅改摘要绕过；恢复前说明备份后新增经验的保留方式。
5. 目录名策略（D3，2026-09-09 定）：老安装目录保留不动（避免改名导致客户端注册失效）；
   新装统一 review-evolution；plan-install/install 的 --target 按实际目录名指定，两种目录名
   均按 update-brief 适配。
   **2026-09-11 用户确认**：最终对外安装的目录名与 SKILL.md `name` 均为 **`review-evolution`**；
   包内顶层目录名必须与之一致。开发/本机继续使用 `wb-review-evolution`，两者 lineage 相同
   （`wb-review-evolution`），因此多端经验整合仍按同一条演化线识别。`build_public.py` 自本版起
   产出 `canonical_name=review-evolution`、`name: review-evolution` 的公开候选。
