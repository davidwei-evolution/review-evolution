# 兼容与降级边界矩阵

核对日期：2026-09-09；适用本地 v0.21.5-beta.1（旧基线受控 bootstrap 策略定稿，纯文档/
版本清单变更）。本表区分功能存在、合成验证与真实环境验证，不依赖用户取得开发目录才能
理解限制。

## 身份与数据格式

最低起点 v0.15.0-beta.1（已发布基线）。核心系列 modular-1，核心 core_api=1，data_schema=1；profile、installation、pack 的格式版本为1。S1偏好政策 plan-a-v1；仅S1偏好事件计分。

包的 core_api 与核心清单字段分别解释：含S2分类字段的包标记core_api=2（API2），不含时为API1。新核心支持两类；无分类支持的旧核心拒绝API2包。包的拒绝保护不等于旧核心直接读取新版档案也有同样保护。

## 升级入口选择（2026-09-09 明确）

- v0.15.0-beta.1（已发布基线）自带的更新器缺少 --reviewed-manifest 与门禁身份表放行
  （即第二轮升级复盘 P2/P3），跨版本新增组件时**不能由旧更新器自身完成** plan-install；
  agent 不应为绕过而给旧更新器/旧门禁打补丁。
- 该基线的可行升级路径（2026-09-09 用户确认 A 方案）：首选“受控 bootstrap”——官方
  digest 核验 + 用户逐次授权后，运行候选包自带更新器 plan-install/install（见
  update-brief“旧基线受控 bootstrap”）；用户拒绝/验签失败/平台禁止时，兜底为备份原核心
  与完整私人档案 → 按本表“升级与恢复操作边界”受控核心替换（沿用原 profile，不复制/
  重建档案）→ 新核心 verify + 经验读写复核。
  v0.15.0→v0.19 数据保留已有 2026-09-07 本机合成验收；v0.15.0→v0.21.2 更新器语义
  已由 2026-09-09 合成验证；v0.19→v0.21.4 无数据格式/schema 变化（data_schema=1、
  core_api=1）。
- v0.21.2 起自带更新器支持 --reviewed-manifest：同代内后续跨版本若新增组件，可按
  update-brief 完成迁移审查后由更新器事务安装，不再需要补丁变通。
- 真实第二环境/官方 Release zip 的端到端升级与失败恢复仍按 003/009 待真实验收。

## 升级与恢复操作边界

1. 升级前保存原核心和完整私人档案；v0.15.0没有整档案backup命令，不能要求它调用后来新增的入口。可在停止写入后由Agent受控复制完整档案到独立位置，逐文件核验，或使用另行验证的中间升级路线。手工目录副本不冒充backup.json格式备份。
2. 核验候选核心身份、版本和实际数据兼容，再沿用原私人目录。不得用空骨架覆盖，不自动改profile_id。
3. 档案不丢失是验收项：受控 bootstrap 与核心替换都必须在升级前后记录并核验档案基线
   （revision/records/effective_preferences 与整目录摘要）；新版续写后不能仅切回旧核心并
   假定能读所有新增内容。需核对降级边界；恢复旧备份前说明其后新记录的保留方式；任何失败
   都保留原档案与核心备份，不以删除/重建经验目录作为恢复手段。
4. 正式backup格式恢复必须取得reader_core对应的完整核心。文档小改也改变完整摘要；v0.20.3备份不能由v0.20.4直接restore。按[工作流](workflow.md)从对应核心恢复到新目录并核验后再决定绑定，不编辑摘要绕过。

确认来源与内容完整性不是证据真实性认证；不执行未知备份中的文件。升级、备份、恢复、绑定是不同步骤，不能以其中一步成功宣称整条旅程完成。
